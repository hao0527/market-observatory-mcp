# Agent instructions

Read README.md and docs/WORK_DEPLOY.md before deployment.

- This is a market-data collector, normalizer and MCP server. Keep market interpretation and investment decisions with the calling AI.
- Preserve source, observation time, successful-fetch time, delivery time, units, change baseline, source transitions, partial failures and degraded-cache flags.
- Never fill missing data with sample prices or mix a CFD/spot/futures contract into one historical series without identifying the instrument change.
- New deployments belong to the current user. The public hosting manifest intentionally has no project_id. Create a new Sites project exactly once, then persist the returned identifier locally. Never copy another person's Site identity, tokens or deployment metadata.
- A public GitHub repository does not imply a public deployed Site. Use owner-private Sites hosting by default and the private MCP plugin generated by Sites.
- Use the current installed Sites skill and its helpers. Resolve the helper root from the installed plugin; do not hardcode the original author's absolute paths. Do not run an empty-project starter setup over this existing source tree.
- D1 binding DB is required for persistent last-success fallback. Apply schema-only Drizzle migrations through the Sites deployment flow. Do not commit a live database or cache payloads.
- After changes, run npm test, npm run test:cache, npm run typecheck and an appropriate production build. Live-source availability is separate from deterministic test success.
- Public exports must pass node scripts/check-public-source.mjs. Keep deployment identities, credentials, build output and runtime state out of the public repository.
- Calendar coverage is intentionally explicit. Refresh verified calendars with primary sources instead of silently guessing future holidays.
